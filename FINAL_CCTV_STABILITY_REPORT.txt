1. EXACT REASON SCREENSHOT 1 BECAME SCREENSHOT 2                          FOUND (real evidence)

Screenshot 1 -> 2 happened on the server running on this LAPTOP (the only server with
Original mode -- production does not have it yet). That server lost its connection to

connections to the NVR failed until the network came back. What you saw

Why the connection was lost -- TWO network problems, both measured:

    all 6 streams of my 10-minute test froze together (item 13).

 b) The office side of the public path (router / port forwarding / uplink) refuses
    new inbound connections every ~20 s. TCP connects to the forwarded NVR ports
    (the same check the server's network monitor does) failed on 17 of 110 tries,
    in a steady rhythm (t = 17, 20, 39, 42, 61, 83, 86, 106, ... s), with others
    taking up to 3 s -- while the internet (1.1.1.1) answered 110/110. Both NVR ports
    fail at the SAME moments (t = 13, 33, 36, 54, 73, 93, 96, 116, 136 s), so it is
    the office router / uplink, not one NVR. The Cloudflare path to production also
    dropped (item 12) while this laptop's internet was fine.

The laptop reaches the NVRs through that office public IP (CCTV_ACCESS_MODE resolves to
the public path off the LAN), so its RTSP streams cross BOTH weak links. Its own
status API recorded exactly these failures as the last error of its workers:
  "stream dropped (no frame within read timeout)"   Original cam 9, 14, 25; Standard cam 4, 15, 25
  "TCP connect to NVR failed (TimeoutError)"        Original cam 2, 3, 4, 8, 10, 15, 17, 18, 19, 20, 23
  "CCTV NETWORK UNREACHABLE"                        (monitor: 3 failed checks + ping failed)

Several Original workers were opened 7-9 times (cams 4, 8, 11, 15, 20, 25): repeated
reconnects. During the same period the production server on the LAN did not
reconnect a single stream (items 12-14).

The grid "LIVE -> CACHED -> CONNECTING on several cameras at once": same cause --
several cameras failing together is the signature of a shared network outage.

Contributing (not the cause): at the time your laptop server and production were
pulling from the same NVRs (up to 11 streams per NVR at 23:06 / 23:22, beyond the

The wrong label: the cached picture said "Connecting..." because the Original viewer's

"Stalled - waiting for video", "NVR unreachable", "Waiting for NVR slot...".

4. PRIORITY SYSTEM                                                        PASS (offline + synthetic)
==========================================================================================
Explicit values (a free NVR slot goes to the highest waiter):
  FULLSCREEN_ORIGINAL 100   FULLSCREEN_STANDARD 90   GRID_ORIGINAL 82   GRID_STANDARD 80
  -- only these have viewers: they are ACTIVE and are NEVER preempted --
  HANDOFF 40 (bridge of a quality switch)   RECENT 30   LINGER 25 (Original kept briefly)
  BACKGROUND_WARM 20   CACHE_REFRESH 10   IDLE 0
Rule enforced in code: a worker can only be stopped for someone else if it has 0
viewers (pool: stop_bg() refuses a worker with viewers; on-demand: only 0-viewer
holders are preempted). Background warming stops when viewers need every slot
(budget = cap - viewed). Tests: 6 viewed tiles on a full NVR survive background churn
and two waiting viewers with no transition at all; a background worker yields its
slot at once (viewer LIVE in ~0.2 s). "Other browsers' viewers" cannot be told apart
from "this browser's" by the server -- every connected viewer is ACTIVE.

7. DUPLICATE STANDARD / ORIGINAL WORKER HANDLING                          PASS (offline + synthetic)
==========================================================================================
  Standard -> Original: the Standard stream stays as the BRIDGE (viewer sees it,
    labelled "switching to Original") until the first Original frame; then it is

  Original -> Standard: make-before-break -- the Original keeps running and the
    Standard viewer gets the LIVE Original picture at Standard size until its own
    Standard stream is live; then the Original is released (HANDOFF_DONE). The viewer

  The pool never re-promotes the Standard stream of a camera watched in Original.
  An Original with no viewer lingers 5 s (reopen = no new handshake), preemptable.

9. STALE THRESHOLD BEFORE / AFTER                                         PASS (unchanged, justified)
==========================================================================================
  before: 2.5 s (CCTV_LIVE_MAX_AGE_S)   after: 2.5 s
  Measured on the LAN (production, sampled every 2 s): max frame age 410 ms over 10 min
  with 6 viewed cameras, 968 ms over 15 min fullscreen -- 2.5 s is 2.6x the worst.
  At 8 fps that is 20 frame intervals, so one late frame never marks a stream stale
  (offline: 1.5 s gaps -> only LIVE, nothing logged). A real stall is now logged the
  moment it crosses the threshold, with the cause: "LIVE -> STALLED
  reason=NO_FRAME_AGE_2515MS (connection open, waiting for data from the NVR/network --
  last packet 2454 ms ago)" or "... frames still arriving but not published
  (CPU/encoder)". If the server must run over the public path, raise
  CCTV_LIVE_MAX_AGE_S to 4-5 s there.
