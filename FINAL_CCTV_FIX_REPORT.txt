VIEWER MODEL (why some checklist items don't apply)
---------------------------------------------------
A "viewer" here is an open HTTP /stream connection. When the browser closes it
(tab close, navigation, page change, clearing img.src), the server's next write
fails and the viewer is removed immediately in a `finally` block. There is no
separate watch/heartbeat/unwatch or sendBeacon to get wrong — connection close IS
the unwatch. So sections about heartbeat expiry, sendBeacon parsing, and
watch/unwatch endpoints do not apply; cleanup is inherent and immediate.

1. ROOT CAUSE (exact)  -- three distinct causes found and fixed
========================================================================
CAUSE A (server, NVR slot held across retries):
In server.py the RTSP worker (_run) acquired an NVR semaphore slot and then held
it across connection-failure retries: on `not cap.isOpened()` it did
`sleep(2); continue` WHILE STILL HOLDING THE SLOT, and held it for the entire
(up to 8s) blocking VideoCapture open. So an offline camera permanently occupied
a slot, and a slot was not freed when a viewer left mid-connect. New views then
sat on "Waiting for NVR slot..."; a manual refresh dropped ALL connections at once
so slots drained and the fresh page connected -- why "refresh makes it work".

CAUSE B (client, leaked MJPEG connections on redraw):
The grid was rebuilt with innerHTML, which DESTROYS <img> elements without
aborting their multipart/x-mixed-replace connections. The browser kept streaming
to the detached images, so viewers/NVR slots leaked (observed: one camera at
viewers=3, an off-page camera holding a viewer). Verified via /api/status.

CAUSE C (client, MJPEG per-host connection-limit deadlock on page change):
Six live MJPEG <img> streams use all ~6 of the browser's HTTP/1.1 per-host
connections. Switching page reassigned all six srcs at once; the browser could not
open the new streams because the old ones still held every connection slot -> the
new page never loaded (page hung). Verified in the real browser (page 2 never
connected; screenshot timed out).

SECONDARY (same-camera fullscreen restart race): the old open_() cleared ALL grid
tiles including the clicked camera, so its worker could stop then re-acquire a slot
and wait behind siblings.

8. SERVER RESTART RECOVERY
========================================================================
Client: every grid <img> has onerror -> retryTile() which re-requests the stream
after 2s (cache-busted); the fullscreen <img> has the same retry. When the server
is stopped the images error and keep retrying; when it returns, the next retry
succeeds and video resumes with no user action.
Server: all state is in-process; a restart starts with a clean NVR limiter and no
workers, and no FFmpeg subprocesses are used by this app (OpenCV/FFmpeg runs
in-process), so there are no orphan processes to leak.
STATUS: CODE VERIFIED. REAL BROWSER: NOT VERIFIED.

9. BROWSER BACK / FORWARD
========================================================================
Back/forward re-renders the page (fresh /stream connections). Same guarantees as

STATUS: CODE VERIFIED. REAL BROWSER: NOT VERIFIED.

10. MULTIPLE TABS
========================================================================
Each open /stream connection is an independent viewer of the shared per-camera
worker. Closing one tab removes only its own viewer(s); the worker keeps running
while any other tab still watches, and stops when the last viewer across all tabs
leaves. No cross-tab session id is shared, so one tab cannot remove another's
viewer.
STATUS: CODE VERIFIED (viewer-count model). REAL BROWSER: NOT VERIFIED.

========================================================================
11. NVR SLOT ACQUIRE / RELEASE
========================================================================
- BoundedSemaphore(CCTV_NVR_MAX_CONN) per NVR (default 6, UNCHANGED).
- Slot taken only for an active attempt; released in `finally` after every
  attempt/lost connection and immediately when the last viewer leaves.
- Live count tracked in NVR_ACTIVE and exposed at /api/status.
- Fullscreen "priority" is achieved structurally: entering fullscreen frees the 5
  other grid slots and reuses the clicked camera's slot, so fullscreen never waits
  behind grid thumbnails. NVR_MAX_CONN was NOT increased.

========================================================================
12. FFMPEG / WORKER CLEANUP
========================================================================
This app uses OpenCV's in-process FFmpeg (cv2.VideoCapture), not a spawned ffmpeg
process, so there are no child processes to kill or orphan. cap.release() is
always called in `finally`; the worker thread exits when _running is cleared.

KNOWN LIMITATIONS
- A camera whose NVR is reachable but whose specific CHANNEL is dead (e.g. no
  camera on that channel) shows "Connecting..."/"OFFLINE" and holds a slot for up
  to ~5s per connect attempt before releasing for a 2s backoff. It does NOT
  permanently hog a slot (verified: slots drain), but leaving such a page can take
  a few seconds for those particular slots to fully drain. This is inherent to
  OpenCV's blocking VideoCapture open and does not affect live cameras.
- The grid is MJPEG over HTTP/1.1, so at most ~6 tiles stream at once (browser
  per-host connection limit). PER=6 is at that limit; a full page's tiles ramp up
  over the first ~2-5s. Going higher (e.g. a 4x4 layout) would require HLS or
  HTTP/2 (as the separate grav-cctv-next app uses). Not needed for the 6-per-page
  layout here.
- The MJPEG <img> retry is a fixed 2s retry (recovers from server restart), not
  exponential backoff.
- Running TWO server instances on the same port (Python allow_reuse_address lets
  this happen) splits state and breaks /api/status readings -- run exactly one.
