How it was tested
  * Offline: 8 suites with fake NVRs (they now reproduce every real-NVR behaviour
    found below) -- 505 checks, 0 failures.
  * Real NVRs: a separate check server on 127.0.0.1:8013 (the working-tree code,
    synthetic live video, REAL playback; outbound connections limited to the NVRs'
    LAN addresses), driven like the page (search API + the real WebSocket). Saved
    frames were compared with the camera's burned-in clock (OSD). The /playback page
    was also used in the in-app browser. The user's own server on :8000 was never
    touched.
  * The NVRs were only read: no setting, recording or clock was changed.

WARNINGS:
  1. Capacity was measured on the dev laptop only (i7-13620H, shared with the :8000
     server): 3 cameras at 1x play smoothly, 4 fall behind. Defaults: 3 per server
     (CCTV_PLAYBACK_MAX_WORKERS), 2 per NVR. Measure on the Alienware before raising.
     A decoder >3 s behind skips to the next key frame instead of lagging further.
  2. Public path not tested end to end (see above).
  3. The NVR accounts in .env are administrators: create live + replay-only accounts.
  4. NVR clocks are 34-40 s slow (NTP off); footage is labelled with that clock.
  5. Shown time vs the camera clock: within ~1-1.5 s (seeks land on the key frame
     before the target, 2 s GOP); up to ~3 s right after an NVR1 recording gap.
  6. The NVRs themselves can be slow: NVR2 delivered at 40-60 % of real time in two
     runs, NVR1 stopped answering for ~3 min once (both while the user's server was
     also using them); playback continued / recovered without errors.
  7. Office-LAN search is slow for many cameras: "Select all" 16-45 s.
  8. 2x / 4x = key frames only (~1-2 pictures/s) and no audio; 0.5x is not offered.
  9. On the LAN the gaps are drawn from the NVR search; outside the office they are
     only found while playing (DESCRIBE cannot see them).
 10. The browser's full-screen API could not be checked in the embedded test browser;
     the in-page full-screen view (one camera, 1280 px, controls kept) works.
 11. The user's :8000 server was restarted by the user at 15:34:50 and runs this code.
     The production server (cctv.grav.in) is unchanged: nothing committed/deployed.
 12. Search results are cached 45 s (a recording that appears later needs a new
     search after that).
