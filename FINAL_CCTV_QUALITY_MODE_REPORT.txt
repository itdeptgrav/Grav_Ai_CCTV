SUMMARY
==========================================================================================
* Header switch [ Standard | Original ]; Standard is the default (also for any new
  browser); the choice is remembered per browser (localStorage), never server-wide.
* Original = the NVR MAIN stream (subtype=0). VERIFIED on the real cameras, not
  guessed: every healthy camera opened in Original delivered 2560x1440 (4 MP) frames,
  while Standard (subtype=1) is 1280x720 on NVR2 and only 352x288 on NVR1, sent as
  640x360. That 352x288 is why NVR1 cameras (e.g. "Corridor office", NVR1 ch14)
  looked soft in fullscreen: Original has 36x the pixels there.
* Visual proof with real frames of the same camera, 1-6 s apart:
    data\quality-test\COMPARISON_nvr1ch3_standard_vs_original.jpg
    data\quality-test\COMPARISON_nvr1ch5_standard_vs_original.jpg
  (data\ is gitignored -- these images never go to GitHub)
* Cost, measured on real cameras: a full-size Original tile is 400-720 KB per frame
  = 19-36 Mbps to the browser at 6 fps and ~0.9 CPU core; Standard is 19-30 KB per
  frame = 1.3-1.9 Mbps and ~0.18-0.26 core. => Original is meant mainly for
  fullscreen. Grid tiles in Original now get the main-stream picture scaled DOWN to
  1280 px wide (never up); fullscreen always gets the full 2560x1440.
* Automated tests: 281 checks, all PASS (5 suites). No worker/slot leak, per-NVR
  cap never exceeded in any test.
* Measurement safety: in this phase NO new NVR connection was opened by me. Real data
  came from (a) the status APIs of the running servers and (b) extra viewers attached
  to streams that were ALREADY running (shared workers -> zero extra NVR load).

13. FALLBACK BEHAVIOR                                                     PASS (offline) / real: observed on dead channels
==========================================================================================
* Only when the main stream FAILS (failed open / pre-flight / no frame, camera
  offline, NVR down, login refused): the viewer gets the Standard stream with a burned-in
  label "STANDARD - Original unavailable"; fullscreen pill "Original unavailable -
  showing Standard". It is never marked as live Original. When the main stream works
  again the viewer switches to Original by itself and the Standard stand-in is released.
* NOT a fallback: waiting for an NVR slot (labelled "Original waiting for NVR slot";
  a Standard stream would need the same slot) and a live stream that dropped and is
  reconnecting (no extra Standard connection for a sub-second gap).
  Bug found + fixed during testing: an earlier version fell back after 8 s of
  waiting, which made a queued tile hold its Standard stream and block its own
  Original slot; and it fell back on every short reconnect. Both covered by tests
  now (the reconnect test was run against the old rule and fails there).
* Real: dead channels in your session (NVR2 ch7/12/13, NVR1 ch10): Original failed ->
  Standard stand-in -> also offline -> honest "Camera offline" card. A HEALTHY camera
  whose main stream fails could not be forced safely: NOT TESTED on real.

==========================================================================================
14. NVR SLOT EFFECT                                                       PASS (offline) / real warning
==========================================================================================
* An Original stream is a normal NVR connection: it counts toward the same per-NVR
  cap (6), and its slot is taken BEFORE connecting (strict cap).
* Slot priority: Original fullscreen 5 > Original grid 4 > Standard fullscreen 3 >
  Standard grid 2 > recently viewed 1 > background 0. Nothing that is being watched is
  stopped to make room; the pool frees BACKGROUND slots, one Original at a time.
  Background workers are always Standard; Original is never kept in the background.
* If watched streams hold every slot, the Original waits and says so (pill + label).
* Offline: peak 6/6 per NVR, cap never exceeded in any test.
* REAL WARNING: the cap is per server. Production's persistent pool holds 6 per NVR
  permanently, so anything else on the same NVRs comes on top. Observed via both status
  APIs: 23:06 NVR2 = 6 (production) + 5 Original (laptop) = 11; 23:22 NVR1 = 6 + 5 = 11.
  It worked, but it is beyond the verified-safe 6. Test on ONE server at a time.
