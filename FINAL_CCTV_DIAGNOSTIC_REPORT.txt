1. EXACT ROOT CAUSES (proven)
--------------------------------------------------------------------------------
R1  4 CHANNELS HAVE NO LIVE VIDEO (hardware / camera side).            PROVEN
    NVR2 ch7 ("NVR2 Cam 7"), NVR2 ch12, NVR2 ch13, NVR1 ch10.
    The NVR accepts the TCP connection and answers the unauthenticated DESCRIBE
    with a 401 challenge in ~10-60 ms (like every channel), but NEVER answers the
    authenticated DESCRIBE. Same result from OpenCV (hits its 8 s timeout). No
    software change can produce video for these; check those cameras/cabling/PoE.
    These are the tiles that "never come" on pages 2, 3 and 4.

R2  OpenCV OPENS ARE SERIALIZED PROCESS-WIDE, AND NVR2 IS SLOW TO     PROVEN
    ANSWER A "COLD" CHANNEL -> cameras appeared one by one, ~4 s apart, and a
    dead channel (R1) blocked every camera behind it for 8 s.
      * NVR2 answers DESCRIBE for a cold channel in 2.8-3.3 s (it starts pulling
        the camera substream on demand); while ANY other connection to that
        channel is open (even an idle DESCRIBE-only one) it answers in 12-56 ms.
        (4/4 channels tested; warmth ends the moment the other connection closes.)
      * NVR side is NOT the limit: 6 cold handshakes in parallel on NVR2 finish in
        3.7 s (22.6 s one-by-one); per-handshake time unchanged (3.18 s vs 3.16 s).
        => "six simultaneous opens overload the NVR" is FALSE.
      * OpenCV IS the limit: 1, 2 or 6 opening threads all take ~23-32 s for 6
        NVR2 cameras, in the same ~4 s staircase.
      * Consequence measured on the old server: page 2 first camera 10.7 s,
        page 3 8.9 s, page 4 10.5 s, and page 5 (ONE camera that opens in 1.4 s)
        took 10.2 s because page 4's dead channel was still inside an
        un-interruptible 8 s OpenCV open holding the serialized path. Dead tiles
        sat on "Connecting..." for 20+ s before their first attempt even started.

R3  NVR2 INTERMITTENTLY DOES NOT ANSWER HEALTHY CHANNELS.              PROVEN
    Observed on ch1, ch2, ch3, ch4, ch5, ch9 at different times (also with strictly
    one-at-a-time handshakes, so not caused by our concurrency). Sometimes the
    answer is just slow (one healthy answer took 6.1 s, one 7.5 s); sometimes no
    answer at all for 8 s, then the next attempt succeeds. This is why the list of
    "dead" cameras changed between yesterday and today (ch4, NVR1 ch7/ch12 were
    "dead" yesterday, healthy today). In the old code each such hang also held the
    global open path for 8 s. NVR-side; see recommendations (section 23).

R4  BROWSER RELOAD DEADLOCK (UI bug, existed before too).               PROVEN
    Each MJPEG <img> holds one of the browser's 6 HTTP/1.1 connections to the host
    for its whole life. On reload the browser keeps the old page (and its 6
    streams) until the NEW page has loaded -- which needs a 7th connection. Result
    measured in the real browser: reload hung ~7 minutes, zero requests reached
    the server, until the tab was closed. Looks exactly like "cameras never come".

R5  BROWSER THROTTLES LOW-PRIORITY IMAGE LOADS; AN MJPEG IMAGE NEVER    PROVEN
    FINISHES -> held-back tiles may wait forever. Measured in the real browser
    (after R4 had occurred): only 3 of a page's 6 stream requests were even sent;
    the other 3 were held inside the browser for 43 s in one case and >80 s
    (never, until closed) in another, although the browser had a free connection.
    A/B in the same browser state: with fetchpriority=high all 6 were sent in the
    same second. (The exact trigger inside the browser is not proven; the first
    load of the session opened all 6 at once. Plausible on the hosted site over the
    public internet too -- NOT TESTED there.)

R6  LATENT UI BUG: tile retry URL broken when the page has no ?key=.   PROVEN
    onerror retry built '/stream/5&_r=...' (no '?'), which the server rejects
    as a bad camera id, so a tile that errored once never recovered. Harmless today
    (the page uses ?key=), but the .env now says access is moving to CMS SSO
    (no ?key= in the URL) -- then every errored tile would stay dead.

R7  "WAITING FOR NVR SLOT..." -- NOT REPRODUCIBLE ON THE BASELINE.     PROVEN
    No slot leak on commit e0b9450: across 1->2->3->4->5->1 (headless and real
    browser) both NVRs dropped to 0/6 after every page cleanup, no stale owners.
    The earlier "Waiting for NVR slot" came from the older slot-before-open design

    HOSTED site, that server is likely running older code (NOT TESTED here).

  NOT changed: nvr_config.py, netcheck.py, .env, NVR_MAX_CONN (still 6).
  NOTE .env.example has an UNCOMMITTED change that is NOT from this work (CMS SSO
  keys) and it contains the REAL CCTV_SSO_SECRET value -- do not commit it as is.

  server.py changes in detail:
   * Pre-flight before every OpenCV open (rtsp_preflight.py): authenticated
     DESCRIBE, run in parallel OUTSIDE OpenCV's global open lock.
       - dead channel -> no answer -> "Retrying..." / "Camera offline", backoff,
         NEVER enters the serialized open path (cannot delay other cameras);
       - healthy -> the connection is held open (idle, no video transferred) until
         the camera's OpenCV open is done, keeping the NVR channel warm: the OpenCV
         open's DESCRIBE is answered in ~20 ms instead of ~3 s (open ~1.3 s).
       - aborts within 0.25 s when the viewer leaves (a hung OpenCV open cannot).
   * Credential safety: until an NVR has accepted the credentials once, its
     pre-flights run one at a time; a 401 pauses that NVR for 15 min -> wrong
     credentials cause ONE failed login, never a burst that locks the NVR account.
     Credentials are confirmed in the background at startup.
   * Slot ownership tracking + waiter tracking + owner dump on wait + leak alarm.
   * Status vocabulary: Connecting... | Waiting for NVR slot... | NVR unreachable |
     Camera offline | Retrying... | LIVE | NVR login failed | Idle, with the
     masked last error per camera. First failure of a previously-fine camera =
     "Retrying..." (R3); repeated or known-dead = "Camera offline"; a camera that
     was dead on a recent visit shows "Camera offline" at once.
   * Retry back-off 1,2,4,8,16,30 s (no slot / no gate held while waiting); sleeps
     end immediately when the viewer leaves.
   * Frame max-age (CCTV_FRAME_MAX_AGE_S, 5 s): the last frame is kept briefly for
     hand-offs (page/fullscreen) but never shown frozen after a feed dies.
   * Placeholder (status) image encoded once per status change, not per viewer
     per frame.
   * Decode: grab() every frame, retrieve()+resize+JPEG only for published frames;
     1 FFmpeg decoder thread per camera; steady STREAM_FPS pacing (see 12.).
   * RTSP over TCP enforced even when OPENCV_FFMPEG_CAPTURE_OPTIONS is pre-set.
   * Removed CAP_PROP_BUFFERSIZE=1: measured unsupported by the FFmpeg backend
     (cap.set returns False for all 25 cameras) -- it was a no-op.
   * /stream responses send "X-Accel-Buffering: no" (nginx must not buffer MJPEG).
   * Logs (CCTV_LOG_EVENTS, default on, never per frame): viewer connected/
     disconnected with counts, worker start/stop, state changes with reason,
     one-line startup breakdown per camera, first live frame sent per viewer,
     slot waits with owners. CCTV_LOG_REQUESTS=1 adds per-request/TCP logging.
   * Startup banner no longer prints the ?key= token.
   * Page JS (no redesign): stopAllStreams() on beforeunload/pagehide (R4);
     fetchpriority=high on stream <img>s (R5); retryUrl() works with and without
     ?key= (R6); fullscreen frees the other tiles BEFORE opening its stream.
